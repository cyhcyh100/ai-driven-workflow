# 저는 AI를 이렇게 사용합니다

2025년 11월부터 2026년 8월까지 9개월간의 Claude Code 세션 기록을 분석해 정리한
작업 방식입니다. 데이터는 프롬프트 10,302건, 세션 트랜스크립트 122개(513MB),
커스텀 스킬 저장소의 커밋 이력, 세대별 `CLAUDE.md`, 프로젝트별 memory 파일
105개입니다.

회사 프로젝트명과 사내 데이터는 일반화했습니다. 인용은 세션 기록을 바탕으로
표현을 다듬었고, 날짜를 병기했습니다.

## 핵심 원칙 열 가지

10,302개의 프롬프트에서 반복적으로 나타난 패턴을 원칙으로 정리했습니다.

| # | 원칙 | 내용 |
| --- | --- | --- |
| 01 | 추측하지 않고 확인한다 | "가능성 있음"으로는 결론을 내리지 않는다. 코드베이스를 열고, 클라우드 콘솔에 로그인하고, DB를 조회해서 증거를 가져온다. 사실과 추론은 구분해서 보고한다. |
| 02 | 구현 전에 계획, 계획 전에 조사 | 거의 모든 작업이 "계획 세워줘"로 시작한다. 조사가 끝나기 전에는 계획을 세우지 않는다. 원인과 비용을 먼저 확인해야 "안 한다"는 결정도 가능하기 때문이다. |
| 03 | 근본 원인만 수정한다 | lint disable, 임시 패치, 다른 레이어에서의 우회는 수정으로 치지 않는다. 같은 문제가 반복되면 접근을 바꾸고, 재현하는 실패 테스트부터 만든다. |
| 04 | 테스트 통과를 완료로 보지 않는다 | 완료 기준은 실제 배포 환경에서 API를 호출하고 실제 결과가 도착하는 것까지다. 에이전트에게 스스로 검증할 수 있는 도구를 준다. |
| 05 | 구현자와 리뷰어를 분리한다 | 구현자의 보고는 검증되지 않은 주장으로 취급하고, 검증은 컨텍스트를 비운 새 에이전트가 한다. 사람이 쓴 plan도 같은 방식으로 검증한다. |
| 06 | 복잡성을 늘리지 않는다 | 오버엔지니어링을 피하고 최소 수정으로 해결한다. 주석에는 코드만 읽어서는 알 수 없는 이유만 남긴다. |
| 07 | 위임에는 사후 보고를 붙인다 | "알아서 쭉 진행해" 뒤에는 "임의로 정한 것 중 리스크 있던 것을 근거와 함께 보고해"를 붙인다. 잘못된 결정을 되돌릴 지점을 파악하기 위해서다. |
| 08 | 조용한 실패를 막는다 | 에러보다 조용히 잘못된 결과가 나오는 상황이 문제다. 판단이 애매하면 fail-closed로 멈추고, 멈춘 이유를 보고하게 한다. |
| 09 | 실패를 규칙으로 남긴다 | 한 번 겪은 문제는 `CLAUDE.md`, memory, 스킬에 규칙으로 적어 재발을 막는다. 금지 규칙에는 이유와 대안을 함께 적는다. |
| 10 | 글도 코드처럼 관리한다 | 티켓은 기획자 기준, 보고는 경영진 기준으로 상세도를 조절한다. 과장하지 않고, 모르면 모른다고 쓴다. 정직성 기준은 코드와 같다. |

## 표준 워크플로우

2026년 중반에 자리잡은 작업 단위입니다. 세션 하나가 티켓 생성부터 머지, 실환경
검증까지를 다룹니다. 세션당 사람 발화는 평균 7.7턴입니다.

실제로 수십 회 반복된 한 줄 지시:

```text
/goal /writing-plans 진행하고 /subagent-driven-development 로 작업한 뒤
/jira finish 로 마무리하고 /molin-review-loop 돌리고 완료되면 머지해.
```

```text
현황 파악
  → /jira                        티켓 생성
  → /writing-plans               계획을 파일로
  → /subagent-driven-development task별 구현자·리뷰어 분리 실행
  → /jira finish                 커밋 + PR
  → /molin-review-loop           AI 리뷰 봇이 approve할 때까지 반영·재리뷰
  → 머지
  → 실환경 검증                   실제 API 호출, 실제 결과 수신 확인
```

이 파이프라인에는 세 가지 특징이 있습니다.

- **계획은 파일로 받는다.** 122개 세션에서 plan mode 승인(`ExitPlanMode`)은
  0회입니다. 계획을 `docs/superpowers/plans/*.md` 파일로 쓰게 하고 에디터에서
  직접 리뷰합니다.
- **병렬 세션은 저장소 복제로 만든다.** 같은 저장소를 `m1`~`m5`, `c1`~`c3`처럼
  복제해 세션 5개를 동시에 돌립니다. worktree는 사용해 본 뒤 번거롭다고 판단해
  전역 규칙으로 배제했습니다. 세션 간 인계는 `HANDOFF.md` 파일로 하고, 인계
  문서도 받은 쪽에서 먼저 검증합니다.
- **컨텍스트는 초기화하고 지식은 파일로 남긴다.** `/clear` 613회, `/compact`
  16회. 압축 대신 초기화를 쓰고, 남길 지식은 `CLAUDE.md`, spec, plan, memory
  파일로 옮깁니다.

## 원칙의 근거

각 원칙의 출처가 된 실제 프롬프트 발췌입니다.

**추측하지 않고 확인한다** (2026-04-13, 인프라 장애 조사)

> 재현은 안되고 있고, 클라우드 콘솔은 읽기 전용 계정으로 로그인해뒀으니까
> 조회만 해서 원인을 파악해줘. DB도 readonly 유저로만 접속해. 확실한 증거를
> 가지고 말해줘야 해. "가능성 있음"은 필요 없어.

**근본 원인만 수정한다** (2025-11-26, 협업 캔버스 POC)

> ESLint를 disable하는 방향은 안 돼. 근본 원인을 파악해서 수정해줘.

**테스트 통과를 완료로 보지 않는다** (2026-07-27, 서비스 API)

> 이 기능을 스테이징에 배포했어. 실제 환경에서 직접 테스트해서 확인해줘. 실제
> API를 호출해서 정상 케이스와 엣지 케이스를 목록으로 만들고 하나씩 전부 검증한
> 다음, 케이스별 결과를 정리해서 보여줘.

**구현자와 리뷰어를 분리한다** (2026-05-28, 코드리뷰 플랫폼)

> 단계마다 컨텍스트를 초기화한 에이전트를 띄워서 검증을 꼭 돌려줘.

커스텀 [subagent-driven-development](../skills/subagent-driven-development/SKILL.md)
스킬에도 같은 지시가 들어 있습니다: "implementer의 보고는 코드에 대한 검증되지
않은 주장으로 취급하라."

**복잡성을 늘리지 않는다** (2026-06-25, 코드리뷰 플랫폼)

> 복잡성을 늘리지 않는 최소한의 수정으로 해결하고 싶어.

**위임에는 사후 보고를 붙인다** (2026-07-31 / 2026-08-04, 음성 인식 서버)

> 더 이상 물어보지 말고 알아서 진행해서 최선의 결과를 만들어줘. 토큰 사용량은
> 신경 쓰지 마.

> 작업이 끝나면 임의로 결정한 것 중 리스크가 있었던 항목을 추리고, 그렇게 선택한
> 이유를 정리해서 브리핑해줘.

**실패를 규칙으로 남긴다** (2026-02-23, 인프라)

> 이런 일이 다시 발생하지 않도록 CLAUDE.md를 업데이트해줘.

**글도 코드처럼 관리한다** (2026-07-20 / 2026-07-28)

> 티켓에 변수명이나 함수명은 필요 없고, 기획자가 읽을 수 있는 수준으로 작성해줘.

> 불필요한 말 없이 스펙 내용만, AI가 쓴 티가 나지 않게 작성해줘.

## 9개월의 진화

수동 지시에서 시작해 자체 하네스를 만들기까지, 반복되는 판단을 도구로 옮기는
방향이 일관됩니다.

### 2025-11 ~ 12 · 로그 복붙 디버깅에서 spec 기반 루프로

협업 캔버스 POC를 만들던 시기. 초반에는 콘솔 로그를 통째로 붙여넣고 원인을
묻는 방식이었고, 12월에 spec 문서 기반 개발 루프가 자리잡았습니다. spec 파일을
번호로 만들어두고 "spec 04 진행해줘"로 지시하며, `/clear`로 작업 단위를
격리합니다. 그룹화 버그를 계기로 "재현 테스트 먼저" 원칙이 생겼습니다.

### 2026-01 · 사이클의 스킬화

계획 → 구현 → 리뷰 → 커밋 사이클이 매 작업에 정착했고, 매번 손으로 치던 지시를
`/commit`과 `/review-changes` 스킬로 만들었습니다. 개인 프로젝트에서 먼저
실험하고 검증된 것을 회사 코드베이스로 가져오는 패턴도 이때 시작됐습니다. 같은
diff를 일관성, 중복, 주석, 정합성 등 관점을 바꿔가며 여러 번 리뷰시키는 습관이
생겼습니다.

### 2026-02 ~ 03 · 닫힌 루프 설계와 코드리뷰 플랫폼 개발 시작

2월 2일 "에이전트가 스스로 컴파일·린트·실행·검증까지 수행할 수 있는 닫힌 루프를
설계한다"는 목표를 세웠습니다. AI 리뷰의 오탐을 다시 AI로 검증하는 레이어가
생겼고, 3월 24일 "코드리뷰 → 수정 → 재리뷰 반복을 자동화하고 싶다"는 문제
인식에서 사내 AI 코드리뷰 플랫폼 개발이 시작됐습니다. superpowers 같은 외부
하네스도 이 시기에 도입했습니다.

### 2026-04 ~ 05 · 인프라 작업 확대, 리뷰 기준 표준화

역할이 기능 개발에서 인프라·플랫폼 관리로 확장된 시기. 클라우드 리전 정리와
비용 절감을 맡으며 "안전하게"라는 지시가 자주 등장하고, 읽기 전용 제약과 실행 전
근거 요구가 강해졌습니다. 리뷰 수용 판단은 매번 쓰던 자연어 지시에서
APPLY/PARTIAL/DECLINE 프레임워크로 정리됐고, 이후 코드리뷰 플랫폼의 MCP 서버에
팀 표준으로 등록됐습니다.

### 2026-06 ~ 08 · 하네스 완성, 위임 범위 확대

6월 9일 리뷰 반영 루프 스킬을 만들면서 워크플로우 전체가 스킬로 고정됐습니다.
티켓부터 머지까지를 한 줄 지시로 처리하고, 코드리뷰 플랫폼 자체 개발에도 그
플랫폼의 리뷰를 사용합니다. 7월 6일에는 토큰 비용 문제를 계기로 역할 기반 2-tier
모델 정책을 설계했고, 7월 10일에는 외부 종합 프레임워크를 제거하고 커스텀 스킬을
git 저장소로 관리하기 시작했습니다. 7월 말부터는 "물어보지 말고 알아서
진행하되, 임의 결정은 근거와 함께 보고하라"는 위임 방식을 씁니다.

## 하네스 구성

반복되는 결정을 미리 스킬과 규칙에 적어 두어, 에이전트가 세션 중에 판단할 일을
줄이는 방향으로 구성했습니다.

### 스킬을 git으로 관리한다

`~/.claude/skills/` 디렉토리 자체가 git 저장소입니다(2026-07-10 초기화).
superpowers 스킬 7개를 한국어로 포크·개조했고, 자작 워크플로우 스킬 8개를 별도로
만들었습니다. 스킬에 딸린 셸 스크립트에는 테스트가 있습니다. 커밋 메시지 예시:
"fix: 스윕 에이전트 3차 리뷰 지적 10건 수정". 이 저장소는 그중 공개 가능한
부분의 스냅샷입니다.

### CLAUDE.md 변천: 6.3KB → 1.8KB → 2.1KB

2026년 4월의 `CLAUDE.md`는 외부 프레임워크가 자동 생성한 6.3KB짜리 능력
카탈로그였습니다. 7월 10일 이를 전부 삭제하고 직접 쓴 정책 2개만 남겼습니다.
이후 추가된 조항은 실제 문제(`AskUserQuestion` preview 버그)에서 나온
하나뿐입니다. 능력 설명은 스킬 파일에 두고, 전역 문서에는 선택과 금지 규칙만
적습니다.

### 역할 기반 2-tier 모델 정책

superpowers 원본은 task 난이도에 맞는 가장 싼 모델을 고르고 실패하면 모델을
올립니다. 이와 반대로 구성했습니다. 실행 역할(implementer, fixer)은 특정 tier
고정, 판단 역할(리뷰어)은 세션 모델 상속. tier는 역할이 결정하고, 막히면
컨텍스트를 보강해 다시 보냅니다. 세션 모델만 바꾸면 리뷰만 상위 모델로 받을 수
있습니다.

### 자체 코드리뷰 하네스

사내 AI 코드리뷰 플랫폼은 Slack 봇, GitHub PR 리뷰 봇, 웹 대시보드, MCP 서버로
구성됩니다. 관점별 리뷰어를 병렬로 돌리고, 오탐을 자체 판정하고, 개인화된 반영
기준을 서버에 저장합니다. 리뷰가 끝나면 지적 반영 → 커밋 → 재리뷰 → CI 확인을
수렴할 때까지 반복하는 자율 수정 루프를 돌릴 수 있고, 머지는 수렴한 경우에만
사람이 별도로 승인합니다. 설계 판단은
[AI 코드리뷰 파이프라인 설계](ai-code-review-pipeline.md)에 정리했습니다.

### 자율성의 범위

기본값은 자율 진행입니다. "계속할까요? 같은 질문과 중간 진행 요약은 상대의 시간
낭비다"가 스킬에 명문화돼 있습니다. 사람이 개입하는 지점은 두 곳입니다. 되돌릴
수 없는 행동(설계 승인, 파괴적 삭제, 무인 push의 개시), 그리고 자기 작업을
자기가 검증하게 되는 지점. 위험도에 따라 자율성 수준도 다르게 줍니다. 회사
프로덕션에는 "읽기 전용으로, 안전하게"를 붙이고, 개인 프로젝트에는 "공격적으로
이용해도 괜찮아, main에 직접 푸시해"를 줍니다.

## 사례

### AI 리뷰가 spec을 바꾼 사고

2026-08-04, 자동 리뷰 반영 루프가 합의된 UI 문구를 바꿨고 QA에서 발견됐습니다.
티켓을 직접 reopen하고 잘못을 먼저 알린 뒤 다음 날 오전까지 수정했습니다. 자동
리뷰가 코드 품질을 고치면서 합의된 spec까지 바꿀 수 있다는 사실이 확인됐고, 무인
루프에 "DECLINE은 정직하게" 같은 안전장치를 두는 근거가 됐습니다.

### 하지 않기로 한 결정에 근거 남기기
