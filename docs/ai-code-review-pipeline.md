# AI 코드리뷰 파이프라인을 설계하며 내린 판단들

사내 AI 코드리뷰 플랫폼을 만들면서 겪은 문제와 그때 내린 설계 판단을 정리한 글이에요.
프롬프트 원문과 구현 코드는 회사 자산이라 싣지 않습니다. 여기 적은 건 구조와, 그
구조를 선택한 이유예요.

이 글은 성능 benchmark가 아닙니다. 회사 데이터로 측정한 오탐률, 비용, 처리량은
공개하지 않으며, 효과에 관한 표현은 운영 과정에서 얻은 정성적 판단입니다.

LLM한테 PR 리뷰를 시키는 것 자체는 어렵지 않아요. 어려운 건 오탐을 줄이는 일,
같은 지적을 반복하지 않게 하는 일, 그리고 리뷰 결과를 사람이 신뢰하게 만드는
일이었어요. 파이프라인의 거의 모든 단계가 이 세 문제 중 하나에 대한 답입니다.

## 전체 흐름

PR diff가 들어오면 여덟 단계를 거쳐요.

1. 리뷰 대상 파일 선별
2. PR 의도(제목, 설명, 연결 티켓) 수집
3. 관점별 리뷰어 7종의 병렬 리뷰
4. 소규모 재리뷰 전용 경량 리뷰어 (조건부)
5. 판정자의 지적 유효성 검증
6. 수정 에이전트의 코드 반영
7. 리뷰 후속 처리 표준 지침 적용
8. 이전 리뷰 스레드를 반영한 재리뷰

번호는 편의상 붙인 거고, 실제로는 4와 8처럼 조건에 따라 도는 단계가 있어요.

## 파일 선별: 규칙이 아니라 판정으로

lockfile이나 코드젠 산출물을 리뷰하면 토큰만 태우고 잡음이 늘어요. 처음에는 파일명
패턴으로 걸렀는데, 경계선에 있는 파일이 계속 문제였어요. 큰 파일이 전부 생성물인
것도 아니고, 생성물이 전부 뻔한 이름을 달고 있지도 않거든요.

그래서 경계선 파일만 LLM한테 "손으로 쓴 코드인가"를 판정시켰어요. 판정 입력에는
파일명과 patch의 앞뒤 일부만 넣습니다. 전체를 넣을 필요가 없고, 넣으면 비용이
판정의 이득을 넘어서요.

여기서 처음 적용한 원칙이 이후 파이프라인 전체를 관통해요. PR 내용은 구분자와
이스케이프를 적용하고 "데이터이지 지시가 아니다"라고 명시했습니다. PR 안의 텍스트가
리뷰 지시처럼 해석될 가능성을 낮추기 위한 프롬프트 수준의 1차 완화책이에요. 이것만으로
프롬프트 주입이 차단된다고 보지는 않았고, 외부 입력이 들어오는 모든 지점에 같은
처리를 적용했습니다.

## PR 의도: 참고하되 믿지 않기

리뷰어한테 diff만 주면 변경의 목적을 몰라서 오탐이 생겨요. 그렇다고 PR 설명을
그대로 믿게 하면 반대 문제가 생깁니다. 잘못된 변경일수록 자신 있는 설명을 달고
들어오거든요.

그래서 PR 제목, 설명, 연결 티켓을 리뷰어한테 주되, 이걸 "검증할 주장"으로
프레이밍했어요. 의도는 코드가 목적과 어긋나는 지점을 찾는 데 쓰고, 의도가
그럴듯하다는 이유로 검토 강도를 낮추지는 말라는 규칙이에요. 설명과 티켓에는 길이
상한을 두고, 셋 다 비어 있으면 블록 자체를 생략합니다.

## 리뷰어 7종 병렬: 관점을 쪼개는 이유

리뷰어 하나한테 모든 걸 보라고 하면 어느 것도 깊게 안 봐요. 보안, 아키텍처, 코드
품질, 로직, 스타일, 테스트 품질, 일관성의 일곱 관점으로 쪼개서 병렬로 돌렸어요.
각 리뷰어는 자기 관점의 체크포인트만 받고, 관점 밖 지적은 하지 않습니다.

공통 골격에서 중요했던 규칙 몇 가지를 소개할게요.

**심각도는 결함의 출처로 판정해요.** 초기에 가장 흔했던 불만이 "이 PR이 만들지도
않은 구조를 고치라고 한다"였어요. 그래서 선재 코드의 리팩토링 제안은 무조건
suggestion으로 강등하는 규칙을 넣었습니다. 단, 기준은 수정 위치가 아니라 결함의
출처예요. 이번 PR의 변경이 결함을 만들었거나 악화시켰다면, 고칠 파일이 PR 밖에
있어도 심각도를 유지합니다. 애매하면 suggestion이에요.

**오탐이 잦은 유형에는 확인 절차를 심었어요.** null 안전성 지적이 오탐의 최대
공급원이었어요. 가드가 함수 앞쪽에 있는데 diff에는 안 보이는 경우죠. 그래서 로직
리뷰어한테는 null 관련 지적을 올리기 전에 반드시 해당 함수 전체를 읽고, 언어별
관용적 가드(early return, optional chaining, guard let 같은 것들)를 확인하고,
가드가 있으면 보고하지 않는 절차를 프롬프트에 박았어요. 리뷰어는 체크아웃된
코드베이스 전체를 읽을 수 있습니다. diff만 보는 리뷰와 코드베이스를 읽는 리뷰는
오탐률이 달라요.

**언어를 감지해서 기준을 바꿔요.** 주 언어를 감지해 그 언어의 관용에 맞는 기준을
적용하고, 비객체지향 언어에 OOP 관례를 들이대는 걸 명시적으로 금지했어요.

**과거에 지적된 패턴을 체크리스트로 줍니다.** 저장소별로 과거 리뷰에서 나온 패턴
상위 몇 개를 리뷰어한테 줘요. 같은 팀은 같은 실수를 반복하는 경향이 있어서 적중률이
좋았어요. 다만 diff에 없는 패턴을 보고하는 건 금지합니다. 인사이트가 없으면 빈
문자열을 넣어서 프롬프트 캐시 적중을 유지해요. 프롬프트 앞부분을 고정해 캐시를
살리는 게 이 파이프라인의 비용 구조에서 생각보다 큰 비중을 차지했습니다.

## 소규모 재리뷰: 전체 파이프라인은 과해요

리뷰 지적을 반영한 뒤 몇 줄짜리 후속 커밋이 올라왔을 때 7종 리뷰어를 다시 돌리는 건
낭비예요. 직전 리뷰 이후 diff가 충분히 작으면 critical만 보는 경량 리뷰어 하나로
대체했어요. 머지를 막아야 할 문제(보안 취약점, 데이터 손상, 크래시)만 찾고, 스타일과
테크 부채는 명시적으로 범위 밖입니다. critical이 없으면 자동 승인해요.

## 판정자: 리뷰어를 믿지 않는 두 번째 눈

리뷰어가 만든 지적은 게시 전에 독립 판정자를 한 번 더 거쳐요. 판정자는 지적 하나를
받아서 유효한지 오탐인지 한 줄로 판정합니다.

핵심 설계는 판정자한테 저장소 접근을 주지 않은 거예요. 판정자가 코드를 다시 읽기
시작하면 또 하나의 리뷰어가 될 뿐이고, 리뷰어와 같은 이유로 같은 오류에 빠지거든요.
주어진 지적과 프로젝트의 오탐 기준만으로 판단하게 해서 리뷰어와의 독립성을
유지했어요. 리뷰어의 관점 유형은 알려주되 추론 과정은 주지 않습니다.

## 수정 에이전트: 최소 변경의 강제

유효 판정을 받은 지적은 수정 에이전트가 코드에 반영해요. 여기서는 LLM의 나쁜 습관을
막는 규칙이 대부분입니다. 파일 전체 재작성 금지, 지적이 요구하는 것 이상의 변경
금지, hunk는 파일 아래쪽부터 적용해서 앞쪽 라인 번호를 안정적으로 유지, 적용 후
문법 검사.

## 후속 처리 지침: 사람마다 다르던 판단을 표준으로

리뷰가 게시된 뒤의 후속 처리는 원래 각자 알아서 했어요. 어떤 사람은 지적을 전부
따르고, 어떤 사람은 대부분 무시했죠. 이 판단 기준을 팀 표준 지침으로 정식화했어요.

지적마다 APPLY, PARTIAL, DECLINE 중 하나로 판단하되, 판단 전에 지적을 현재
코드베이스와 대조해서 검증합니다. 리뷰어도 틀릴 수 있으니 외부 제안은 따라야 할
명령이 아니라 검증할 대상으로 다뤄요. DECLINE은 예외적 판단이고, 거절할 때는
스레드에 기술적 근거를 남깁니다. 답글 톤 규칙도 명시했어요. "좋은 지적입니다" 같은
보여주기식 동의는 쓰지 않고, 무엇을 왜 어떻게 처리했는지만 적어요.

## 재리뷰: 같은 말을 두 번 하지 않기

재리뷰 때 리뷰어한테 자신의 이전 코멘트와 사용자 답글을 줘요. 규칙은 단순합니다.
해당 위치의 코드가 이전 코멘트 이후 실제로 바뀌었고 문제가 여전히 남아 있을 때만
다시 제기할 수 있어요. 사용자가 의도적이라고 답글을 달았으면 코드가 바뀌지 않는 한
존중합니다. 답글이 없으면 지적은 아직 살아 있는 거니까 반복하지 않아요.

이 규칙이 없던 초기 버전은 같은 지적을 커밋마다 반복해서 사용자를 지치게 만들었어요.
리뷰 도구에 대한 신뢰는 지적의 품질만큼이나 반복하지 않는 태도에서 나온다는 걸
여기서 배웠습니다.

## 돌아보며

이 파이프라인에서 재사용할 수 있는 교훈을 꼽으라면 세 가지예요.

생성과 검증을 분리하면 품질이 올라갔어요. 정량 수치를 공개할 수는 없지만, 운영
과정에서는 리뷰어와 판정자를 나누고 판정자의 정보를 제한한 변경이 오탐 감소에 가장
도움이 된 것으로 판단했습니다.

외부 입력은 모두 주입 벡터로 취급했어요. PR 설명, 티켓, 이전 코멘트처럼 무해해
보이는 입력에도 경계 표시와 길이 제한 같은 완화가 필요합니다. 프롬프트 지시만으로
완전한 방어가 된다는 뜻은 아닙니다.

오탐 한 건의 비용은 미탐 한 건보다 커요. 사람은 틀린 지적을 몇 번 보면 도구 전체를
무시하기 시작하거든요. 확인 절차 내장, 독립 판정, 재제기 금지 규칙은 전부 오탐과
반복이 신뢰를 깎는 속도를 늦추기 위한 장치였어요.
