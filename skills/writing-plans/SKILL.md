# Writing Plans

## 개요

우리 코드베이스에 대한 컨텍스트가 전혀 없고 취향도 미덥지 않은 엔지니어가 실행한다고 가정하고, 빠짐없는 구현 plan을 작성한다. 그 엔지니어에게 필요한 모든 것을 문서화한다: 태스크별로 어떤 파일을 건드리는지, 코드, 테스트, 참고할 문서, 테스트 방법. plan 전체를 잘게 쪼갠 태스크로 제공한다. DRY. YAGNI. TDD. 잦은 commit.

실행자는 숙련된 개발자이지만 우리 툴셋과 문제 도메인은 거의 모른다고 가정한다. 좋은 테스트 설계에도 익숙하지 않다고 가정한다.

**시작 시 선언:** "writing-plans 스킬로 구현 plan을 작성하겠습니다."

**작업 위치:** 현재 워크스페이스에서 새 브랜치를 만들어 작업한다 (worktree 사용 안 함).

**plan 저장 위치:** `docs/superpowers/plans/YYYY-MM-DD-<feature-name>.md`
- (사용자가 다른 위치를 지정하면 그쪽을 따른다)

## 범위 점검

spec이 서로 독립적인 여러 서브시스템을 다룬다면, 브레인스토밍 단계에서 서브 프로젝트별 spec으로 쪼개졌어야 한다. 그렇지 않았다면 서브시스템당 하나씩 별도 plan으로 나누자고 제안한다. 각 plan은 그 자체로 동작하고 테스트 가능한 소프트웨어를 만들어내야 한다.

## 파일 구조

태스크를 정의하기 전에, 어떤 파일이 생성·수정되고 각 파일이 무엇을 책임지는지 먼저 그린다. 분해 결정이 확정되는 지점이 여기다.

- 경계가 분명하고 인터페이스가 잘 정의된 단위로 설계한다. 파일 하나에 책임 하나.
- 한 번에 컨텍스트에 담을 수 있는 코드가 추론하기 쉽고, 파일이 집중되어 있을수록 편집도 안정적이다. 너무 많은 일을 하는 큰 파일보다 작고 집중된 파일을 선호한다.
- 함께 바뀌는 파일은 함께 둔다. 기술 레이어가 아니라 책임 기준으로 나눈다.
- 기존 코드베이스에서는 정착된 패턴을 따른다. 코드베이스가 큰 파일을 쓰고 있다면 일방적으로 재구성하지 않는다 — 다만 수정 대상 파일이 이미 감당 못 할 만큼 커졌다면 분리를 plan에 포함하는 것은 합리적이다.

이 구조가 태스크 분해의 근거가 된다. 각 태스크는 독립적으로도 말이 되는 자기완결적 변경을 만들어내야 한다.

## 태스크 크기 조절

태스크란 자체 테스트 사이클을 갖고, 새로운 리뷰어의 관문을 통과할 가치가 있는 최소 단위다. 태스크 경계를 그을 때: 셋업, 설정, 스캐폴딩, 문서화 단계는 그 산출물이 필요한 태스크 안에 접어 넣는다. 리뷰어가 이웃 태스크는 승인하면서 이 태스크만 의미 있게 반려할 수 있는 지점에서만 쪼갠다. 각 태스크는 독립적으로 테스트 가능한 산출물로 끝난다.

## 잘게 쪼갠 스텝 단위

**스텝 하나는 액션 하나 (2~5분):**
- "실패하는 테스트를 작성한다" — 스텝
- "실행해서 실패를 확인한다" — 스텝
- "테스트를 통과시키는 최소 코드를 구현한다" — 스텝
- "테스트를 실행해서 통과를 확인한다" — 스텝
- "commit한다" — 스텝

## Plan 문서 헤더

**모든 plan은 반드시 이 헤더로 시작한다:**

```markdown
# [기능 이름] 구현 Plan

> **For agentic workers:** REQUIRED SUB-SKILL: subagent-driven-development(권장) 또는 superpowers:executing-plans를 사용해 이 plan을 태스크 단위로 구현할 것. 스텝은 진행 추적을 위해 체크박스(`- [ ]`) 문법을 사용한다.

**Goal:** [무엇을 만드는지 한 문장]

**Architecture:** [접근 방식 2~3문장]

**Tech Stack:** [핵심 기술/라이브러리]

## Global Constraints

[spec의 프로젝트 전역 요구사항 — 버전 하한, 의존성 제한, 네이밍·문구 규칙,
플랫폼 요구사항 — 항목당 한 줄, 정확한 값은 spec에서 그대로 복사한다.
모든 태스크의 요구사항에 이 섹션이 암묵적으로 포함된다.]

---
```

## 태스크 구조

````markdown
### Task N: [컴포넌트 이름]

**Files:**
- Create: `exact/path/to/file.py`
- Modify: `exact/path/to/existing.py:123-145`
- Test: `tests/exact/path/to/test.py`

**Interfaces:**
- Consumes: [이 태스크가 앞선 태스크에서 가져다 쓰는 것 — 정확한 시그니처]
- Produces: [뒤 태스크가 의존하는 것 — 정확한 함수명, 파라미터·반환 타입.
  각 태스크의 구현자는 자기 태스크만 볼 수 있으므로, 이웃 태스크가 쓰는
  이름과 타입은 이 블록을 통해서만 알 수 있다.]

- [ ] **Step 1: 실패하는 테스트 작성**

```python
def test_specific_behavior():
    result = function(input)
    assert result == expected
```

- [ ] **Step 2: 테스트를 실행해 실패 확인**

Run: `pytest tests/path/test.py::test_name -v`
Expected: FAIL with "function not defined"

- [ ] **Step 3: 최소 구현 작성**

```python
def function(input):
    return expected
```

- [ ] **Step 4: 테스트를 실행해 통과 확인**

Run: `pytest tests/path/test.py::test_name -v`
Expected: PASS

- [ ] **Step 5: Commit**

```bash
git add tests/path/test.py src/path/file.py
git commit -m "feat: add specific feature"
```
````

## 플레이스홀더 금지

모든 스텝에는 엔지니어에게 실제로 필요한 내용이 들어 있어야 한다. 아래는 **plan 실패**다 — 절대 쓰지 않는다:
- "TBD", "TODO", "나중에 구현", "세부사항 추후 작성"
- "적절한 에러 처리 추가" / "검증 추가" / "엣지 케이스 처리"
- "위 코드에 대한 테스트 작성" (실제 테스트 코드 없이)
- "Task N과 유사" (코드를 반복해서 적는다 — 엔지니어가 태스크를 순서대로 읽지 않을 수 있다)
- 어떻게 하는지 보여주지 않고 무엇을 할지만 서술한 스텝 (코드를 바꾸는 스텝에는 코드 블록 필수)
- 어떤 태스크에도 정의되지 않은 타입·함수·메서드에 대한 참조

## 기억할 것
- 파일 경로는 항상 정확하게
- 모든 스텝에 완전한 코드 — 코드를 바꾸는 스텝이면 그 코드를 보여준다
- 정확한 커맨드와 기대 출력
- DRY, YAGNI, TDD, 잦은 commit

## 셀프 리뷰

plan을 다 쓴 뒤, 새로운 눈으로 spec을 다시 보며 plan을 대조한다. 이건 직접 수행하는 체크리스트다 — subagent dispatch가 아니다.

**1. Spec 커버리지:** spec의 각 섹션/요구사항을 훑는다. 그것을 구현하는 태스크를 짚을 수 있는가? 빠진 것을 나열한다.

**2. 플레이스홀더 스캔:** 위 "플레이스홀더 금지" 섹션의 패턴들이 plan에 있는지 검색한다. 발견하면 고친다.

**3. 타입 일관성:** 뒤 태스크에서 쓴 타입·메서드 시그니처·프로퍼티 이름이 앞 태스크에서 정의한 것과 일치하는가? Task 3에서는 `clearLayers()`인데 Task 7에서는 `clearFullLayers()`라면 버그다.

문제를 찾으면 그 자리에서 고친다. 재리뷰는 필요 없다 — 고치고 넘어간다. 태스크가 없는 spec 요구사항을 발견하면 태스크를 추가한다.

## 실행 핸드오프

plan을 저장한 뒤, 실행 방식을 선택하게 한다:

**"plan을 완성해 `docs/superpowers/plans/<filename>.md`에 저장했습니다. 실행 옵션은 두 가지입니다:**

**1. Subagent 주도 (권장)** — 태스크마다 새 subagent를 dispatch하고, 태스크 사이마다 리뷰. 빠른 반복

**2. 인라인 실행** — executing-plans로 이 세션에서 태스크를 실행. 체크포인트를 둔 배치 실행

**어느 쪽으로 할까요?"**

**Subagent 주도를 선택하면:**
- **REQUIRED SUB-SKILL:** subagent-driven-development 사용
- 태스크마다 새 subagent + 2단계 리뷰

**인라인 실행을 선택하면:**
- **REQUIRED SUB-SKILL:** superpowers:executing-plans 사용
- 체크포인트를 둔 배치 실행
