# AI 코딩 에이전트 운영 방식

이 문서는 Claude Code를 일상적인 개발 작업에 사용하면서 정착시킨 운영 방식을
설명합니다. 특정 프롬프트를 소개하기보다 작업을 어떻게 나누고, 어디에서 사람이
판단하며, 결과를 어떻게 검증하는지에 초점을 둡니다.

## 문서의 범위

분석 대상은 2025년 11월 4일부터 2026년 8월 7일까지의 기록입니다.

- 사용자 프롬프트 10,302건(중복 제외)
- 세션 트랜스크립트 122개, 513MB
- 커스텀 스킬 저장소의 커밋 이력
- 시기별 `CLAUDE.md`
- 프로젝트별 memory 파일 105개

프롬프트 수와 명령 사용 횟수는 작업 규모와 반복 패턴을 확인하는 데만
사용했습니다. 이 수치만으로 생산성이나 결과물의 품질을 평가하지는 않았습니다.
회사 프로젝트명은 일반화했고 사내 데이터는 제외했습니다. 문서에서 언급하는
개별 사례는 여러 세션에 반복된 요청을 요약한 것이며 원문 인용이 아닙니다.

## 현재 작업 흐름

하나의 세션에서 티켓 작성부터 구현, 리뷰, 실환경 확인까지 진행합니다.

```text
현황과 제약 확인
  → 티켓 작성
  → 구현 계획을 파일로 작성하고 승인
  → task별 구현과 독립 리뷰
  → 커밋과 PR 작성
  → 리뷰 지적 검증 및 반영
  → 사람의 최종 승인과 머지
  → 배포 환경에서 동작 확인
```

개인 환경에서는 이 과정을 `/jira`, `/writing-plans`,
`/subagent-driven-development`, `/molin-review-loop` 같은 명령으로 연결합니다.
일부 명령은 사내 도구이므로 이 저장소에 포함되어 있지 않습니다. 공개된 스킬의
구성과 설치 방법은 [README](../README.md)에서 확인할 수 있습니다.

사람이 반드시 확인하는 산출물은 요구사항, 설계, 구현 계획, 최종 diff입니다.
승인된 계획 안에서 이루어지는 파일 수정과 테스트는 에이전트가 이어서 수행합니다.
계획과 코드가 충돌하거나 되돌리기 어려운 작업이 필요한 경우에는 실행을 멈춥니다.

## 운영 원칙

### 조사 결과와 추론을 구분한다

장애 조사나 인프라 작업에서는 먼저 읽기 전용 접근 범위를 정합니다. 코드, 로그,
클라우드 콘솔, 데이터베이스에서 확인한 사실과 그 사실을 바탕으로 한 추론을 따로
보고하게 합니다. 재현하지 못한 원인은 가능성만으로 확정하지 않습니다.

일반적으로 다음 순서를 사용합니다.

1. 관찰된 현상과 재현 조건을 기록한다.
2. 관련 코드와 운영 데이터를 읽기 전용으로 확인한다.
3. 가능한 원인과 반대 증거를 함께 정리한다.
4. 재현 테스트나 추가 관측으로 원인을 좁힌다.
5. 확인한 원인만 수정한다.

이 순서는 수정하지 않기로 결정할 때도 필요합니다. 예를 들어 DB 커넥션 풀을
늘리지 않기로 했다면 현재 사용량, 병목 여부, 결정을 다시 검토할 조건을 티켓에
남깁니다.

### 계획을 대화가 아닌 파일로 관리한다

구현 전에 저장소와 실행 환경을 조사하고, 결과를 바탕으로 계획을 작성합니다.
계획에는 수정할 파일, 인터페이스 변경, 테스트 방법, 완료 조건을 포함합니다.
계획은 `docs/superpowers/plans/*.md`에 저장해 에디터에서 검토합니다.

분석한 122개 세션에는 Claude Code의 plan mode 승인 기록(`ExitPlanMode`)이
없었습니다. 이는 계획을 생략했다는 뜻이 아니라 계획 검토 경로가 대화형 plan
mode가 아닌 파일이었다는 뜻입니다.

파일로 남긴 계획은 세 가지 용도로 사용합니다.

- 구현자에게 전달할 작업 범위를 고정한다.
- 리뷰어가 구현 결과를 대조할 기준을 제공한다.
- 세션이 중단됐을 때 완료한 task부터 다시 시작하지 않게 한다.

### 구현과 검증의 컨텍스트를 분리한다

각 task는 구현자가 수정하고 별도의 리뷰어가 확인합니다. 리뷰어는 구현자의 설명을
결론으로 받아들이지 않고 계획, diff, 테스트 결과를 직접 대조합니다. 사람이 작성한
계획도 같은 방식으로 검토 대상에 포함합니다.

리뷰는 다음 두 질문을 함께 다룹니다.

- 계획에서 요구한 동작을 빠짐없이 구현했는가?
- 불필요한 변경이나 코드 품질 문제가 추가되지 않았는가?

리뷰어에게는 전체 대화 대신 task brief와 diff package를 전달합니다. 구현 과정의
추론을 그대로 넘기지 않아 같은 가정에 묶일 가능성을 줄이고, 검토에 필요한
컨텍스트의 크기도 제한합니다.

### 완료 조건을 실행 환경까지 확장한다

테스트 통과는 필요한 조건이지만 항상 충분한 조건은 아닙니다. 배포, 외부 API,
권한, 데이터 형식이 관련된 변경은 실제 환경에서만 확인할 수 있는 실패가 있습니다.
이런 작업의 계획에는 다음 항목을 완료 조건으로 둡니다.

- 자동화된 테스트와 정적 검사 통과
- 배포 상태와 로그 확인
- 실제 API의 정상·경계 사례 호출
- 응답과 후속 데이터 기록 확인

프로덕션 접근은 별도 승인과 읽기 전용 원칙을 따릅니다. 실환경 검증이 곧 무인
변경을 허용한다는 뜻은 아닙니다.

### 최소 변경을 기본값으로 둔다

수정은 재현한 원인을 제거하는 범위로 제한합니다. lint 규칙 비활성화, 다른
레이어에서의 우회, 관련 없는 리팩터링은 기본적으로 계획에 포함하지 않습니다.
주석에는 코드만 읽어서는 알 수 없는 제약이나 선택 이유를 남깁니다.

리뷰 지적도 그대로 적용하지 않습니다. 현재 코드와 요구사항을 다시 확인한 뒤
적용, 부분 적용, 거절 중 하나를 선택하고, 거절할 때는 기술적 근거를 기록합니다.
AI 리뷰가 합의된 UI 문구를 일반적인 표현으로 바꾼 사례 이후에는 spec과 충돌하는
리뷰 제안을 명시적으로 거절하도록 규칙을 보강했습니다.

### 반복되는 판단을 저장소에 남긴다

세션 안에서만 유효한 정보와 다음 작업에도 필요한 규칙을 구분합니다. 다시 사용할
정보는 다음 위치에 기록합니다.

| 정보 | 저장 위치 |
| --- | --- |
| 프로젝트 전반의 제약과 금지 사항 | `CLAUDE.md` |
| 합의된 요구사항 | spec |
| 구현 순서와 완료 조건 | plan |
| task 진행 상태 | progress ledger |
| 세션 간 결정 사항과 실패한 접근 | `HANDOFF.md` |
| 반복 실행할 절차 | skill |

금지 규칙에는 이유와 가능한 대안을 함께 적습니다. 규칙이 많아져 찾기 어려워지면
절차는 스킬로 옮기고, `CLAUDE.md`에는 선택 기준과 제약만 남깁니다.

## 세션과 컨텍스트 관리

긴 대화를 계속 압축하기보다 작업 단위가 바뀔 때 컨텍스트를 초기화합니다. 분석
기간에는 `/clear`를 613회, `/compact`를 16회 사용했습니다. 초기화 전에 다음
세션에서 필요한 결정과 미완료 작업을 파일로 옮깁니다.

동시에 여러 작업을 진행할 때는 저장소를 별도 디렉터리에 복제해 세션별 작업 공간을
분리합니다. worktree도 사용해 봤지만 현재 개인 환경에서는 디렉터리와 브랜치의
대응이 명확한 복제 방식을 택했습니다. 이 선택은 보편적인 권장 사항이 아니라 현재
도구와 작업 규모에 맞춘 운영 결정입니다.

## 역할에 따른 모델 배정

task 난이도를 매번 예측하는 대신 역할에 따라 모델 tier를 정합니다.

- implementer와 fixer는 실행용 tier를 사용합니다.
- reviewer처럼 판단이 필요한 역할은 세션 모델을 따릅니다.
- 실패한 task는 바로 상위 모델로 보내기보다 누락된 컨텍스트와 재현 정보를 먼저
  보강합니다.

이 정책은 비용을 예측하기 쉽게 하고 리뷰 품질을 세션 단위로 조절하기 위한
선택입니다. 모델별 비용이나 품질을 비교한 benchmark 결과는 아닙니다.

## 운영 방식이 바뀐 과정

| 기간 | 변경 | 계기 |
| --- | --- | --- |
| 2025-11 ~ 12 | 로그 중심 디버깅에서 spec과 재현 테스트 중심 작업으로 전환 | 같은 유형의 버그가 반복됨 |
| 2026-01 | 계획·구현·리뷰·커밋 절차를 스킬로 분리 | 매 작업에서 같은 지시를 반복함 |
| 2026-02 ~ 03 | 실행과 검증을 닫힌 루프로 구성하고 코드리뷰 자동화 시작 | 리뷰 지적의 오탐과 후속 처리 편차가 큼 |
| 2026-04 ~ 05 | 읽기 전용 조사와 리뷰 판정 기준을 명문화 | 인프라 작업과 플랫폼 운영 범위가 늘어남 |
| 2026-06 ~ 08 | 티켓부터 재리뷰까지 연결하고 역할별 모델 정책 도입 | 긴 작업의 인계 비용과 모델 사용 비용을 줄일 필요가 생김 |

변경의 공통 방향은 세션에서 반복되는 판단을 파일, 스킬, 검증 절차로 옮기는
것이었습니다. 커스텀 스킬은 git으로 관리하고, 변경에는 가능한 경우 테스트를
추가합니다.

## 관찰된 사용 패턴

다음 수치는 분석 기간의 사용 기록을 요약한 것입니다.

| 지표 | 값 | 집계 기준 |
| --- | ---: | --- |
| 사용자 프롬프트 | 10,302 | 2025-11-04 ~ 2026-08-07, 중복 제외 |
| 세션당 사용자 발화 | 7.7회 | 분석한 트랜스크립트 기준 평균 |
| plan 또는 계획 언급 | 1,464 | 사용자 프롬프트의 문자열 출현 횟수 |
| `확인해` 언급 | 675 | 사용자 프롬프트의 문자열 출현 횟수 |
| `/clear` 실행 | 613 | 명령 실행 횟수 |
| 서브에이전트 호출 | 421 | 구현·수정 180회, 리뷰 143회, 기타 98회 |
| 구조화 질문 | 171 | `AskUserQuestion` 호출 횟수 |
| 프로젝트별 memory 파일 | 105 | 분석 시점의 파일 수 |
| 커스텀 스킬 | 15 | superpowers 기반 7개, 직접 작성 8개 |

문자열 출현 횟수에는 문맥이 반영되지 않으며, 서로 다른 작업의 난이도도 보정하지
않았습니다. 따라서 이 표는 사용 습관을 설명할 뿐, 다른 방식보다 낫다는 결론의
근거로 사용할 수 없습니다.

## 한계

- 분석은 한 사용자의 기록에 한정되어 있어 다른 팀이나 프로젝트에 그대로 적용할
  수 없습니다.
- 원본 세션 기록과 사내 프로젝트 데이터는 공개하지 않았으므로 제3자가 수치를
  재현할 수 없습니다.
- 작업 결과의 품질, 소요 시간, 비용 변화를 같은 기간의 대조군과 비교하지
  않았습니다.
- 일부 운영 명령과 코드리뷰 시스템은 사내 도구이므로 이 저장소만으로 전체 흐름을
  재현할 수 없습니다.

이 문서의 수치보다 재사용 가능한 부분은 승인 지점, 컨텍스트 전달 형식, 완료 조건을
명시하는 방법입니다. 각 환경의 권한과 위험 수준에 맞게 이 세 항목부터 조정해야
합니다.
